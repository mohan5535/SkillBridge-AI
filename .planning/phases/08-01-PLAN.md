    - `hashPassword(password)`: validates that `Buffer.byteLength(password, 'utf8') <= 72` (throwing ValidationError if exceeded to prevent bcrypt truncation vulnerabilities); hashes via `bcrypt.hash(password, 12)` using cost factor 12 per AUTH-02.
    - `comparePassword(password, hash)`: validates byte length <= 72, then verifies using `bcrypt.compare(password, hash)`.
    - `generateJwt(payload)`: signs payload containing user_id, email, and role using `jwt.sign(payload, env.JWT_SECRET, { expiresIn: '30m' })` per AUTH-04.
    - `verifyJwt(token)`: verifies and decodes token using `jwt.verify(token, env.JWT_SECRET)`.
    - `generateActivationToken()`: generates 256-bit entropy raw token via `crypto.randomBytes(32).toString('hex')` and computes SHA-256 digest `crypto.createHash('sha256').update(rawToken).digest('hex')`. Returns `{ rawToken, tokenHash }`.
    - `hashToken(rawToken)`: computes SHA-256 hex digest for lookup comparisons.
    - `sanitizeUser(user)`: removes `password_hash`, `activation_token_hash`, and internal credentials before returning client payloads.

    Author unit test `tests/unit/authService.test.js` verifying:
    1. Passwords hashed with bcrypt produce valid hashes verifying with cost factor 12.

    4. Activation token generation produces a 64-character raw hex token and an exact matching 64-character SHA-256 digest.

<task type="auto">
  <name>Task 2: Cookie-Parser Integration & Signed Double-Submit CSRF Middleware</name>
  <files>
    backend/src/middleware/csrf.js,
    backend/src/app.js,
    backend/tests/unit/csrf.test.js
  </files>
  <action>
    Create `src/middleware/csrf.js` implementing the HMAC-signed double-submit cookie pattern per AUTH-06:
    - `generateCsrfToken()`: generates a 32-byte raw token via `crypto.randomBytes(32).toString('hex')` and computes signature `crypto.createHmac('sha256', env.CSRF_SECRET).update(rawToken).digest('hex')`. Returns formatted cookie value `rawToken + '.' + signature` and un-hashed `rawToken` for header matching.
    - `setCsrfCookie(res)`: sets cookie `sb_csrf_token` with value `rawToken.signature`, `httpOnly: false` (readable by client JavaScript), `sameSite: 'strict'`, `path: '/'`, and `secure: process.env.NODE_ENV === 'production'`. Returns `rawToken`.
    - `csrfProtection(req, res, next)`:
      - Allows safe idempotent methods: `GET`, `HEAD`, `OPTIONS` pass through immediately.
      - Intercepts state-changing mutations: `POST`, `PUT`, `PATCH`, `DELETE`.
      - Extracts `rawHeaderToken` from `req.headers['x-csrf-token']`.
      - Extracts `cookieVal` from `req.cookies['sb_csrf_token']`.
      - If either is missing, forwards AppError with HTTP 403 Forbidden (`code: 'CSRF_TOKEN_MISSING'`).
      - Decomposes `cookieVal` into `[cookieRawToken, cookieSignature]`.
      - Computes expected signature `crypto.createHmac('sha256', env.CSRF_SECRET).update(rawHeaderToken).digest('hex')`.
      - Verifies that `rawHeaderToken === cookieRawToken` and `cookieSignature === expectedSignature` using constant-time comparison `crypto.timingSafeEqual`.
      - If invalid or signature mismatched, forwards AppError with HTTP 403 Forbidden (`code: 'CSRF_TOKEN_INVALID'`).

    Update `src/app.js` to register `cookieParser(env.COOKIE_SECRET)` before routing and mount a dedicated CSRF token endpoint `GET /api/auth/csrf-token` providing the signed cookie and header token payload.

    Author unit test `tests/unit/csrf.test.js` asserting:
    1. GET and OPTIONS requests pass through without requiring CSRF headers.
    2. POST request without X-CSRF-Token header is rejected with HTTP 403.
    3. POST request with forged or tampered X-CSRF-Token is rejected with HTTP 403.
    4. POST request with valid X-CSRF-Token matching the signed cookie succeeds.
  </action>
  <verify>
    <automated>node --test backend/tests/unit/csrf.test.js</automated>
  </verify>
  <done>
    CSRF middleware correctly generates HMAC-signed double-submit cookies, allows safe read queries, and enforces constant-time signature validation on all mutating requests.
  </done>
